01 Product

Merchants list products; customers browse, order and pay online; the platform takes a commission per order and settles the remainder to merchants.

This is a marketplace, not a single store — Merchant.commissionRate and a per-item merchantId on every order line commit us to that, and it drives the settlement, per-merchant fulfilment and payout requirements below.

Primary market is Mongolia: MNT pricing, Ulaanbaatar timestamps, mn/en content throughout.

How to read this

Status reflects the current state of market-backend. Much of it was derived from the code rather than written from scratch — the domain model, role matrix and lifecycles are read directly from what is implemented, so they are accurate by construction.

The load-bearing distinctions:

  • Product vs ProductVariant. Product is the catalog entry and is not purchasable. The variant is what is bought — its own SKU, price and barcode. Price range and stock total on Product are denormalized from variants for listing queries.
  • Inventory. available = quantity − reserved, per variant per warehouse. InventoryMovement is an append-only ledger; replaying it must reproduce Inventory.
  • Order is a snapshot. Product name, price, options and address are copied at checkout, so later catalog edits never rewrite history.
  • Cart. Guests are keyed by session and merged into the customer's cart on sign-in.

05 Lifecycles

Order — transitions enforced in code
stateDiagram-v2
    [*] --> PENDING : checkout
    PENDING --> PAID : payment confirmed
    PENDING --> CANCELLED : customer or timeout
    PAID --> CONFIRMED : merchant accepts
    PAID --> CANCELLED
    PAID --> REFUNDED
    CONFIRMED --> SHIPPED : handed to courier
    CONFIRMED --> CANCELLED
    CONFIRMED --> REFUNDED
    SHIPPED --> DELIVERED
    SHIPPED --> REFUNDED
    DELIVERED --> COMPLETED
    DELIVERED --> REFUNDED
    COMPLETED --> [*]
    CANCELLED --> [*]
    REFUNDED --> [*]

An illegal transition is rejected, not logged — the allowed set is declared on the status enum itself, so every service goes through the same rules.

Payment: NEW → PENDING → PAID | FAILED | CANCELLED, then REFUNDED or PARTIALLY_REFUNDED.
Shipment: CREATED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED, with FAILED and RETURNED terminal.

07 Key flows

Checkout — one transaction
sequenceDiagram
    participant C as Customer
    participant API as public-api
    participant INV as InventoryService
    participant DB as MongoDB
    C->>API: POST /v1/orders/checkout
    API->>DB: load cart, re-price from variants
    API->>API: apply coupon, shipping, tax
    loop each item
        API->>INV: reserve(variant, qty)
        INV->>DB: conditional update, available >= qty
        alt insufficient
            INV-->>C: 409 out of stock, with available
        end
    end
    API->>DB: save order PENDING + clear cart
    API-->>C: order with total
Why this matters

The reservation filter itself asserts sufficient stock, so concurrent checkouts cannot oversell without a lock. The whole flow is one transaction — which is why MongoDB must run as a replica set, not a standalone.

Payment confirmation — callbacks are never trusted alone
sequenceDiagram
    participant PR as Provider
    participant API as public-api
    participant GW as PaymentGateway
    PR->>API: POST /v1/payment/callback
    API->>API: resolve invoice id
    alt already PAID
        API-->>PR: 200, ignored
    end
    API->>GW: verify(payment)
    GW->>PR: query payment status
    alt not paid
        API->>API: mark FAILED
    else paid
        API->>API: mark PAID, order PAID
        API->>API: commit reserved stock
    end

09 Open decisions

These block design work and need a human answer. Everything above that says "undecided" points here.

IDDecisionWhy it matters
D1Commission — flat, or per category / per merchant?Changes the settlement model and what we must retain per order
D2Merchant payout — schedule, minimum, who bears refund cost?No payout or settlement entity exists. Core marketplace flow, currently unmodelled
D3Returns — window, who pays return shipping, restocking rules?Drives the entire RMA model in E7
D4Is ebarimt (VAT receipt) issuance required for us?Legal. Adds fields to Order and a hard integration — far cheaper now than retrofitted
D5Personal data retention and deletion policyRequired for E1-S6; Apple requires account deletion for App Store apps
D6Expected volumes — SKUs, orders/day, peak concurrency, uptimeDetermines whether the single-Mongo design holds
D7Delivery — own couriers, a partner, or both? UB vs aimag pricing?Shapes DeliveryProvider implementations and fee rules
D8Which payment methods at launch beyond QPay?Each is a separate gateway implementation
D9Multi-merchant orders — split into sub-orders, or one order?Affects fulfilment, payout and the customer's order view

10 Where the gaps are

Grouped by how much design they need, not by size — the first group is a week of plumbing, the last needs decisions before anyone writes code.

Partial Endpoints over working services

The logic exists and nothing exposes it. Thin work: customer registration, profile and addresses, category management, coupon management, image upload, system config admin.

Partial Stubs that must become real

QPay HTTP calls, payment reconciliation, low-stock alerts, delivery tracking. Shape is defined; the implementations are missing.

Todo Entities with nothing behind them

Brand, Banner, Review, Wishlist, Warehouse, Merchant, Refund. Each needs a service, an API and its rules.

Todo Not modelled — needs design first

Merchant payout and settlement, the returns/RMA workflow, notifications, ebarimt, multi-merchant order splitting, analytics.
